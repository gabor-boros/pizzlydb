# M1 storage gate

This note records what was run in the working tree for Phase 1A. It is not a claim that the nightly soak passed.

## Ran

- `cargo test -p pizzlydb-storage --lib --tests` after the WAL generation reset, shared/exclusive locks, read-only open, checksum page ids, and `NoSpace` degradation. A later `cargo clippy -p pizzlydb-storage -p pizzlydb-graph --all-targets -- -D warnings` passed.
- `tests/ownership.rs`: a second read-write open returns `Locked` until drop; two read-only opens share; `NoSpace` leaves snapshots usable and rejects later batches.
- `vfs_posix` tests: a child process is refused the exclusive lock and takes it after the parent drops it; `open_read_only` and `verify_quick` succeed on mode `0444`.
- `wal::tests::prune_drops_checkpointed_images_and_keeps_the_floor`: a reset leaves stale frames in the file and recovery ignores them. `tests/crash_sim.rs` `wal_reset_does_not_lose_a_full_commit` passed at the default 4 persistence samples.
- The crash-simulation canary `wal_reset_does_not_lose_a_full_commit` asserts that a `Durability::Full` commit is still readable after every sampled crash through checkpoint. Sample count is `PIZZLYDB_CRASH_SAMPLES`, default 4.
- WAL reset writes a new generation header and does not rewrite kept frames. A frame newer than the horizon blocks the reset.
- `space::tests::a_second_bitmap_page_round_trips_and_two_gibibytes_fit` grows the address map until `high_water * 8192` is at least 2 GiB and reloads that bitmap.

## Not run

- 2000-case or 200k-case model suite, 14 consecutive nights, one-hour soak, 16-reader by 100k-commit scale run, 4 GiB RSS, a filled 2 GiB or 16 GiB database file, 1e6-key WAL amplification, ARM64 CI on GitHub, and a 64-committer SSD group-commit benchmark.
- Grouped durability still syncs inside the single open batch. A second `begin_write` stays `Busy` until that batch is dropped.
- Stored B+ tree parent pointers are still on disk. Unchanged parents are not rewritten.
- `Space` is still cloned by value. A bitmap that covered 2^32 pages would be about 512 MiB and would be copied with the allocator. The 2 GiB result above is the address map, not a filled file.
